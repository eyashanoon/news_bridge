Introduction 03 / 22

Project Overview

News Bridge is an AI-driven news aggregation and personalization platform that automates ingestion, enrichment, and delivery of multilingual news from web domains, Telegram channels, and editor-authored content.
  • Java Spring Boot backend as authoritative data & security layer
  • Python microservices for crawling, NLP & RAG
  • React web apps + Expo mobile + Three.js 3D presenter
  • Arabic & English support throughout the pipeline

Problem Statement 04 / 22

The Challenge

Despite many news apps, integrated platforms still fail to solve:

  • Heterogeneous web structures — layouts change; rule-based scrapers break
  • Endpoint discovery — which URLs are listings vs. articles?
  • Multilingual enrichment — Arabic & English need language-aware NLP
  • Implicit personalization — users rarely configure detailed profiles
  • Semantic discovery — keyword search can't answer natural-language questions
  • Telegram channels — primary news source in many regions
  • Engaging presentation — text-only feeds underutilize multimedia
7 persistent problems addressed

Website Pipeline · Step 1 08 / 22

Accepting Roots

  • Admin registers a news domain (name + base URL) via POST /roots
  • Creates a Root entity in MySQL with status ACTIVE
  • Optional trust verification via Wayback, Wikidata, MBFC, and NewsGuard
  • Admin UI lists, edits, and triggers endpoint discovery from registered roots
  • Every crawled article traces back to an administratively approved news domain
Roots are the entry point — the first step in onboarding a new news website into the platform.
Website Pipeline · Step 2 09 / 22

Discovering Endpoints

  • Admin triggers POST /roots/{id}/discover → Python service on port 8004
  • BFS crawl within the domain (depth 2) classifies each page with XLM-RoBERTa
  • Identifies listing URLs (article index pages) vs. individual articles
  • Admin reviews results and bulk-imports chosen URLs as Endpoints

Website Pipeline · Step 3 10 / 22

Crawling Articles

  • Site Crawler (:8000) runs priority-scheduled workers on active endpoints
  • Fetches listing pages → extracts links → deduplicates via cache_endpoints table
  • Page classifier filters article URLs → deep-learning extractor produces structured blocks
  • New articles submitted via POST /articles → creates Article + Post records
  • Fetch stack: curl_cffi browser impersonation → Playwright fallback for JS sites
  • Never-crawled endpoints get highest priority in the worker queue
Website Pipeline · Step 4 11 / 22

Post-Processing

APScheduler job runs every 10 seconds inside the crawler process:

Classification

Posts with no label → assigned to 1 of 7 categories (Politics, Sports, Tech, etc.) + language detection via langdetect

Tag Extraction

Hybrid NER (BERT + CAMeL-BERT for Arabic) + YAKE keywords → stored in PostTags table

Arabic text is normalized before NLP. Enriched posts become eligible for personalized feed ranking and AI vector indexing.
Website Pipeline · Step 5 12 / 22

Constraints 20 / 22

Constraints & Limitations

Resource & Hardware Limits

  • Limited GPU VRAM on development machines — restricts batch sizes, training runs, and concurrent ML services
  • Modest RAM & CPU — typically only one heavy Python service (crawler, classifier, or AI assistant) runs comfortably at a time
  • No cloud GPU budget — entire stack targets local/demo deployment on a single workstation or laptop
  • Long inference times on CPU — post enrichment, embedding, and RAG queries are noticeably slower than a production GPU setup

AI & Model Compromises

  • Small local LLMs via Ollama (quantized) — weaker summarization, Q&A, and translation vs. large cloud models
  • No from-scratch LLM training — RAG and classifiers depend on pre-trained checkpoints and limited labeled data
  • Manual labeling bottleneck — page classifier dataset capped at ~2,400 pages due to time and team size
  • Avatar & TTS quality constrained by offline tooling and lack of a dedicated GPU inference server
Other practical limits: small graduation team · administratively registered sources only (not open-web scale) · Telegram API/session restrictions · Playwright fallback is RAM-heavy on low-spec hardware · no horizontal scaling or 24/7 ops budget
